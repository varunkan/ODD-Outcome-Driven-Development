odd 0.3.0 · early · MIT

An outcome counts as delivered only when its proof fails without the change.

Outcome-Driven Development (ODD): work is done when a proof says so, not when the agent says so. It is one small command and a half-page method for building software with a coding agent. It works with Claude Code, Cursor, Copilot, Codex or anything else that can run a shell command.

Install GitHub Why it exists

The problem

Coding agents report "done" for work that is not done. The tests pass, but they test nothing the change does. The bug is still there, the summary says fixed, and nobody finds out until later. More instructions do not fix this: an instruction is something the model may or may not follow.

The idea

1State the outcome firstOne sentence saying who observes what, a command that exits 0 only when it is true, and the files the change may touch.
2Make the changeThe agent writes the test and the code, inside the files it named.
3odd done decidesIt passes only if the proof passes, fails with the change taken out, and passes again once the change is put back.
4CI recomputes itThe gate re-runs everything from the code and trusts nothing the agent recorded. Every changed file must sit inside a verified outcome.
RefusedA test that asserts nothing, a weakened test, a proof that passes anyway, a hand-written "done", files changed outside the stated boundary.
AcceptedA proof that fails without the change and passes with it, on the code as it is. Or an honest odd park: "this cannot be done as specified".

See it catch one

Real output from launch/demo.sh, shortened.

# the ticket: a bill of 100.00 split three ways loses a cent
$ odd new split "A cashier who splits a bill three ways sees three amounts that add up to the bill." \
    --proof "python3 -m unittest -q tests.test_split" --in "billing/**"

# the agent writes a test that only checks there are three parts, "fixes" the code, says done
$ odd done split
odd: the proof still passes with the change taken out, so it does not depend on the change.
  taken out: billing/split.py

# a real test (the parts add up to the bill) and a real fix
$ odd done split
split: verified. took out 1 file(s), 3 line(s); without them the proof said: FAILED (failures=1)

$ odd gate --recompute --base main      # what CI runs
  ok      split: A cashier who splits a bill three ways sees three amounts that add up to the bill.
PASS

Install

# the command
$ pipx install odd-tool                 # or pip install odd-tool, or download odd.py
$ cd your-project && odd init         # writes .odd/ and the method into AGENTS.md

From there your coding agent follows the method in AGENTS.md by itself. To make it count, add the gate as a required check. On GitHub Actions it is one step:

- uses: actions/checkout@v4
- uses: varunkan/ODD-Outcome-Driven-Development@v0.3.0

The action judges each pull request with its own pinned copy of the tool, never the copy the pull request carries, and reads the settings from the target branch, so a change cannot loosen its own gate. Other CI systems use two lines that odd init prints.

Works with

odd init writes the method into the root AGENTS.md, which Codex, Cursor, GitHub Copilot in VS Code, Claude Code, Junie and Windsurf read without configuration. Gemini CLI, Aider and Copilot Chat outside VS Code need one line. The command and the gate are the same for every tool and for a person. So far only Claude Code has been run with it.

Next to Spec Kit, BMAD and Superpowers

They are good at structure: specs, plans, roles, skills. ODD does one thing they leave to the model.

Does it work better?

Not claimed yet. A same-task comparison is running: 16 tasks with hidden acceptance tests (bug fixes, features, traps, vague requests, impossible ones), each done by plain Claude Code, ODD, Spec Kit, BMAD and Superpowers, three times each, on Sonnet and on Haiku. It measures how often the work really passes, how often each one says "done" when it is not, and the cost in tokens, money and time.

Early signs from the pilot, too small to be results: on Sonnet, plain Claude Code got the work right on every task tried, so correctness may not separate the five; on an impossible task, one framework claimed "done".

The results will be published here with their spread, whatever they show. The harness is open: bench/.

Where it came from

The method was distilled from building a production restaurant point-of-sale system with coding agents over three months: 1,856 instructions given, each catalogued and ruled on. Most were dropped. The two most expensive mistakes in that project were its own process rules, and the waste record is published with the rest of the evidence.

Limits

  • It checks that the proof depends on the change, not that the outcome is worth having or the proof thorough. A person should read the outcome sentence and the proof: they are three lines.
  • On a developer's machine an agent with a shell can bypass any local check. The gate is the authority in CI, as a required check, when the tool and CI settings need review to change and the agent cannot push to the target branch.
  • The check runs the proof three times, so the proof should be the narrowest command that shows the outcome.
  • Evidence so far comes from one project. Windows and macOS are untested.
