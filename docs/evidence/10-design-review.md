# Design review of the lean, portable tool

*Produced 2026-11-11 by four independent critics (Claude Fable 5.2) attacking the first design and the first version of the tool: tamper resistance, the correctness of the take-out check, day-to-day friction, and how each coding tool actually reads instruction files (checked against the tools' own documentation). One judge then ruled which changes were required. Rendered from `data/design-review.json`. Several critics ran probes; those findings say "measured". DESIGN.md version 2 and the current tool implement the ruling.*

## Ruling: proceed-with-changes

### Required changes (23)

1. Section 2 and `odd new`: delete the `base` field. Sections 4 and 5 use one base for both the diff and the counterfactual: the merge-base of HEAD and the target branch (`--base REF` in CI, otherwise the default branch). If it cannot be resolved, exit 2 and print the fetch command; the CI step fetches full history.

   Why: An agent-written base lets a proof go red for reasons unrelated to the change. `base:` set to an old ancestor commit -> the revert removes earlier merged work -> any proof fails -> verified (practitioner probes: 224 unproven lines passed, and 60 lines passed by touching an old outcome). After `git merge main` or a rebase the recorded base also reverts teammates' edits. On a depth-1 checkout the commit is absent, so every pull request is 'could not run'. (from: tamper, practitioner, counterfactual (sections 2, 4.2, 5))

2. Section 5: define in-play in one sentence: an outcome whose file is added or changed since that base. Delete `status` from the file. 'Done' is never written to a committed file: locally it is derived from evidence, in CI every in-play outcome that is not parked is verified again. The only state in the file is `parked: <reason>`. A parked outcome covers no files, so its changes are removed, moved to another outcome or fit the small-change lane, otherwise the gate fails. `odd abort` merges into `odd park`.

   Why: 'In-play' and 'part of this change' are undefined. One note line added to last month's outcome -> it re-verifies against old content and covers today's unproven edit in the same directory. `odd park x` with 400 changed lines left inside `in` -> if parked counts as resolved, unverified code merges. A hand-set `status: done` is a claim inside a tool whose point is that done is not claimed. (from: tamper, counterfactual, practitioner (sections 2, 3, 5))

3. Cut the per-outcome `tests` field and the `--tests` flag. Test files are the files matching one `test_globs` list in the config (current defaults plus `src/test/**`), read from the base revision under `--recompute`. They are never taken out, need no outcome and do not count toward the small-change lane. If the proof command names a file that would be taken out, `odd done` and the gate exit 2 and say to move it under a test path.

   Why: `in: src/billing/marker.py`, `tests: **`, 2,000 changed lines -> only marker.py is reverted, every other file matches `tests`, the gate passes. With a colocated test or a proof script inside `in`, the test is reverted too, the runner reports no tests or no such file, and that counts as red. A 9-line fix passes the lane and the same fix with its 20-line test fails it, so the default rewards leaving the test out. (from: tamper (blocker), counterfactual, practitioner (sections 2, 4.2, 4.3, 6))

4. Cut `real` (with `--real` and the PROVEN label) and `after` (with `--after`). The file is `outcome`, `proof`, `in`, plus optional `counterfactual: skip - <reason>`, `parked: <reason>` and `escaped: <slug>`. Section 2 adds three sentences: paths, globs and the proof are relative to the repository root; the proof is the narrowest command that shows the outcome, never the whole suite; a proof asserts results or counts, not wall-clock time. Lines 41-42 drop '`after:` is the plan'.

   Why: `real: yes` is set by the agent, cannot be recomputed, prints PROVEN (odd.py:603) and feeds a published figure. `after` is written and never read (odd.py:646-647). From packages/api, `--in src/split.py` fails with 'nothing inside in changed' and no hint that paths are root-relative. A 10-minute suite used as the proof costs 30 minutes per check. A 200 ms threshold passes on the laptop and fails on the CI runner. (from: practitioner, tamper (section 2))

5. Sections 4.2 and 4.3 share one definition of the changed set: `git diff --name-status -z --no-renames <base>` plus `git ls-files -z --others --exclude-standard`. Taking the change out means: added or untracked -> moved aside; deleted -> recreated; modified (content or mode) -> base version. All git output is read with `-z`.

   Why: A new, untracked `src/billing/split.py` appears in neither the diff nor a checkout of base, so nothing is taken out, the proof still passes and a correct outcome is rejected; an untracked file outside every boundary passes the local gate (both measured). Without `-z` a non-ASCII path prints quoted and matches no glob. (from: counterfactual (blocker), tamper (sections 4.2, 4.3))

6. Section 4: verification is green, red, green. The proof passes, fails with the change taken out, and passes again once the change is put back. On the reverted tree, exit 126 or 127, death by signal and timeout are 'could not run' (2), not red. An empty revert set exits 1 with 'nothing in `in` changed since base' without a second run. State the cost (three proof runs per outcome), print each run's seconds, and print the expected remaining time after the first run.

   Why: `proof: mkdir out && ./build.sh && ./out/test` passes once and fails on any second run, so it is counted as red although nothing depends on the change (measured). A proof killed or missing on the reverted tree (exit 137, 127) is counted as red. The closing green run also shows the restore gave back a passing tree and rebuilds what the red run left behind (lockfiles, caches). (from: tamper, counterfactual (section 4))

7. Section 4.2 states the rules of the in-place revert. (1) A journal of byte copies (type and mode kept, links as links) is written under the git directory before the first file changes. (2) The revert writes the working tree only, never the index: git writes the base versions (`git restore --source=<base> --worktree`), the tool only moves added files aside. (3) Restore copies back from the journal, in a `finally`, on SIGINT, SIGTERM and SIGHUP, and at the start of any later `odd` command, which then exits 2. (4) A path is restored only if it still holds what the revert wrote; otherwise both versions are kept and named. (5) One lock, so two checks cannot interleave. (6) Any error while reverting -> restore and exit 2; the proof never runs on a partial revert. (7) Every revert and restore write gets a newer mtime, never the old one.

   Why: The proof is killed at the agent's shell timeout mid-check -> the tree holds base content -> the agent re-implements, or runs `git add -A && git commit` and commits the reverted tree with `.odd/tmp/` -> the next `odd` command overwrites the newer edits. `git checkout <base> -- paths` rewrites the index (measured: a staged deletion was un-staged). A same-second, same-size revert makes Python reuse stale bytecode, so a correct outcome is rejected (measured). `git show` writes a symlink as a text file (measured). (from: counterfactual (two blockers), tamper (sections 4.2, 11))

8. Section 4.3: a changed product file may match the `in` of only one in-play outcome; otherwise the gate fails and names both. Outcomes that must touch the same file become one outcome or two successive changes.

   Why: A and B both have `in: src/billing/**`; B's proof is A's test and B's code is absent. B's revert removes A's change as well, A's test goes red, B is verified and both are counted as delivered. (from: tamper; replaces the counterfactual and practitioner variants (sections 4.2, 4.3))

9. Section 4.2: say that a skip is an exemption with a reason, not a verification. Cut `max_skips`. The gate's result line names each skip with its reason and changed-line count. A submodule pointer change cannot be taken out, so it needs a skip.

   Why: `counterfactual: skip - pure refactor`, `proof: true`, `in: src/**` -> any change of any size passes, visible only as a note in a green log. A cap does not close it: one skipped outcome with a wide `in` passes at any cap above zero, and zero blocks every refactor, dependency bump and dead-code removal. (from: tamper and counterfactual, conflict resolved (section 4.2))

10. Section 5: under `--recompute` the tool and the config are read from the base revision (CI step: `git show <base>:.odd/odd.py > $TMP/odd.py`, then run that copy). A change to either is inert in the change that makes it and is printed as 'control files changed'. State that CI is the authority only when (1) the gate is a required check on the target branch, (2) the tool, the config and the CI configuration cannot change without a person, (3) the agent cannot merge or push to the target branch; otherwise the gate is advisory. Add one warning: do not move the job to `pull_request_target`.

   Why: The agent replaces `.odd/odd.py` with `sys.exit(0)`, or writes `{trivial_lines: 1000000, exempt: ['**']}`; both paths are exempt today, so CI runs the fake or recomputes under the attacker's settings and passes. The agent edits the workflow to `run: true`; on `pull_request` the edited workflow is the one that runs, so the check is green and the gate never ran. No in-repo rule closes the second case, so line 86 ('changes nothing') becomes three stated conditions. The tool already does the first half (odd.py:132-146, 576, 843); the design does not say it. (from: tamper (two blockers), practitioner keep-list (section 5))

### The command list

- odd init [--claude-hooks]: installs or repairs. Writes `.odd/odd.py`, `.odd/config.json`, the method block in `AGENTS.md` and the Claude import; prints the CI step and the three conditions. Safe to re-run. Exit 0.
- odd new <slug> "<outcome>" --proof CMD --in GLOBS: writes `.odd/outcomes/<slug>.md` with `outcome`, `proof` and `in`. Exit 0.
- odd done <slug>: green, red with the change taken out, green again; writes local evidence only. Exit 0 verified, 1 not shown, 2 could not run.
- odd gate [--base REF] [--recompute]: every changed product file is inside the boundary of one verified in-play outcome or a printed exemption. Without `--recompute` it runs no proof and lists every outcome in the change. Exit 0 pass, 1 fail, 2 could not run.
- odd park <slug> "<reason>": the one honest exit, for blocked work and for work that cannot be done as specified. A parked outcome covers no files. Exit 0.
- odd stats: counts from outcome files (total, skipped, parked, escaped) plus local attempt counts, labelled self-reported. Exit 0.
- Internal entry point, not a command a person or agent types: `odd hook stop|session-start`, called only by the opt-in Claude Code hooks.

### What ships for each tool in this version

- Always: the method block in the root `AGENTS.md`, rendered from one constant between markers, placed at the top on first insertion. It is the only rendered copy.
- When a Claude instruction file exists: one `@AGENTS.md` import line in the root `CLAUDE.md` or `.claude/CLAUDE.md`, skipped when that file is `AGENTS.md` itself.
- CI, any system: `odd init` prints one step for the project's existing test job (full history, tool taken from the base revision, `gate --recompute --base <target>`) and the three conditions under which CI is the authority. Nothing is written.
- Opt-in, `odd init --claude-hooks`: two Claude Code hooks (turn end, session start) in `.claude/settings.local.json`, per developer, never committed, never installed on detection.
- README only, each labelled untested: the Gemini CLI setting, the Aider `read: AGENTS.md` line, a pointer line for Copilot Chat outside VS Code, and the one line for a personal pre-push hook.
- Not in v1: `.cursor/rules/odd.mdc`, `.github/copilot-instructions.md`, the four skills, the write guard, a git hook installer, a generated workflow file, native Cursor or Copilot hook adapters, `pyproject.toml` or a PyPI release.

### Limits to state plainly instead of engineering around

- CI is the authority only when the gate is a required check, a person owns the tool, the config and the CI configuration, and the agent cannot merge or push to the target branch. Without all three the gate is advisory. No rule inside the repository can protect the CI configuration.
- The change that adopts the tool is judged by its own copy of the tool and by default settings. A person reviews that change.
- The check shows that the proof depends on the change, not that it checks the outcome. For new code any proof that imports the new symbol goes red on the reverted tree. A pre-existing test can be weakened to one the old code still fails. Any non-zero exit counts as red, including a flaky test. The last line of the red run is printed for a person to read.
- The proof is code written by the party being checked, so it can tell the reverted tree from the real one (git state, file hashes). This is not closed. The proof text is in the diff, and the comparison's 'gate passed, hidden tests failed' figure is the size of this hole.
- Coverage is by path. An outcome with `in: **` puts every changed file inside its boundary even when its proof touches one of them. The gate shows lines per outcome; it does not prevent this.
- Exemptions are not verification: the small-change lane (a per-change budget; a run of small changes passes; small is not low-risk), exempt paths (markdown including the instruction file, lockfiles), test files, and skips. Each is printed with its line count.
- State outside tracked files is not reverted. A dependency-only change, a generated file, a cached result or a runner that selects tests from git state shows no difference and needs a skip.
- The proof's test must live in a file of its own under a test path. Tests in the same file as the product (Rust `#[cfg(test)]`, doctests, Zig test blocks) cannot be verified and need a skip.
- The check rewrites files in place. For the length of the red run the tree holds base content, so a dev server, hot reload or file sync sees it, and an editor may write its buffer back. A killed run is restored by the next `odd` command; nothing is destroyed, but displaced copies may be left to sort out.
- Cost is three proof runs per in-play outcome, on every local check and every CI run. A timeout is 'could not run'. An outcome of the form 'the hang is gone' must turn the hang into a failure itself (`timeout 60 <cmd>`). A proof with a timing threshold can fail on a slower runner.
- A proof that needs a real device, account or secret cannot be recomputed in CI and is outside v1. The tool has no 'proven on the real system' label.
- Within one change a file belongs to one outcome. Two outcomes that touch the same file are merged or shipped as successive changes.
- Changes are measured against the target branch. Work committed directly on the target branch is not seen. A shallow clone is 'could not run'. Editing a merged outcome file puts it back in play.
- Requires a POSIX shell, git and python3. Windows, Git LFS and `autocrlf` are untested. A submodule change needs a skip. In a monorepo one gate job needs every toolchain the in-play proofs use.
- Reach of the method. Documented to read a root `AGENTS.md` without configuration: Codex, Cursor, Copilot in VS Code with its cloud agent and CLI, Claude Code (directly, or through the import when a `CLAUDE.md` exists), Junie, Devin/Windsurf. Gemini CLI and Aider need a one-line setting. Zed reads it only when no higher-priority rules file exists. Copilot Chat outside VS Code needs a pointer line. Chat-only surfaces without a shell get the text and cannot run the tool.
- Only Claude Code has been run. The Cursor and Copilot paths are unverified until one recorded run each. Early-feedback hooks exist for Claude Code only, opt-in and per developer; Cursor and Copilot CLI also execute that file on the same machine, which is untested.
- If a Claude instruction file is added later without the import, Claude Code stops reading the method and the only signal is a red gate. Re-running `odd init` repairs it.
- Local evidence can be forged and `odd stats` is self-reported. Every effectiveness figure is unmeasured until the comparison runs, and published figures come only from the benchmark harness.

### Suggestions not adopted, and why

- Keep `base` as a hint checked for ancestry (counterfactual): an old ancestor commit passes the ancestry check, so the 'red for an unrelated reason' attack stays open. Cutting the field is smaller and closes it.
- A finite default `max_skips` read from the base config (tamper): one skipped outcome with a wide `in` passes at any cap above zero, and zero blocks every refactor and dependency bump until the owner loosens it for good. It does not close its own scenario; the skip goes in the result line instead.
- Make `--tests` required and check it against a `test_paths` list (tamper): once it must fall inside the base-config list, the per-outcome field adds nothing. The field is cut and the one list decides.
- Treat a workflow-file change as never trivial and never exempt (tamper): the attack it targets switches the gate off, so the rule never runs, and it would fail every adopter's first pull request. The three stated conditions cover it.
- Run `odd doctor` in the CI step to check the method block, and keep `doctor` to print the conditions and detect a missing Claude import (tamper, portability): a removed method shows up as a red gate, which is the authority; a re-run of `odd init` repairs and reports. No sixth diagnostic command.
- List real-system outcomes as 'not recomputed' with exit 2 (tamper): the tool would need the agent-set `real` label back to know which they are. Stated as a limit instead.
- Per-file counterfactual under `--recompute` (raised and deferred by tamper): one proof run per changed file. Revisit only if the comparison shows unproven lines escaping.
- A both-trees-green check for skipped outcomes (considered by tamper): it does not stop `proof: true`, so it is a mode with no closed failure.
- A deny list for proof text that reads git state or the journal (tamper advises against it): the first draft's list caught 1 of 6. The journal moves out of the work tree and the claim is narrowed.
- Print and record 'red shared with <slug>' for overlapping outcomes (counterfactual), or only state it as a cost (practitioner): both leave the false accept in place. The one-file-one-outcome rule is a single condition and removes it.
- Exit 2 when rename detection pairs a path inside the revert set with one outside (counterfactual): with `--no-renames` counting, the exposure is a moved file small enough to fit the lane. Extra logic for a bounded case; the printed last line of the red run shows it.
- Compare `git status --porcelain` before the revert and after restore (counterfactual): the closing green run already rebuilds what the red run wrote, and the compare raises false alarms on untracked build output.
- Run proofs through Git's `sh` on Windows, hash git blob ids, and add a `python3`/`python`/`py -3` hook launcher (counterfactual): none of it is measured. Windows is stated as untested, and with evidence no longer committed the cross-OS hash mismatch cannot occur.
- A notice 'N uncommitted files outside this outcome were present' (counterfactual): the failure it describes is caught by CI, as the critic says.

- `odd init --ci` writes a GitHub Actions workflow (design, portability): it lacks the project's toolchain, is GitHub-only, and is one more file to keep passing its own gate. The step is printed for the project's existing test job.

- Keep `--hook pre-push` as an opt-in installer (portability): per clone, bypassable with `--no-verify`, absent in cloud agents, blocks unfinished pushes, and needs its own launcher. One README line for a personal hook.

- `odd new --escaped-from <slug>` (tamper): an optional `escaped:` line written by hand records the same thing without a flag.
- Run the gate as the last step of each package's test job in a monorepo (practitioner): each job would run every in-play proof without the other packages' toolchains. Stated as a limit.

### Counterfactual (14 findings)

- **[blocker] 4.2 ("back to their base content") and 4.3 ("computed from git").** MEASURED. The commonest outcome adds a new file and runs `odd done` before committing. Input: `src/billing/split.py` is new and untracked, proof imports it. `git diff --name-status <base>` does not list untracked files at all, and neither `git checkout <base> -- src` nor `git restore --source=<base> --worktree -- src` removes them (probe: `new_untracked.py` survived both). Result: nothing is taken out, the proof still passes on the 'reverted' tree, a correct outcome is REJECTED (false green). The same blind spot means the boundary check in 4.3 never sees an untracked file written outside `in`. 'Base content' is also undefined for deleted files (must be recreated), mode-only changes and renames. *Fix:* Define the changed set once, in one sentence, and use it for both 4.2 and 4.3: `git diff --name-status -z --no-renames <base>` plus `git ls-files -z --others --exclude-standard`. Per status: added or untracked -> moved into the journal directory; deleted -> recreated from base; modified (content or mode) -> base version. `--no-renames` makes a rename a delete plus an add, so no rename logic is needed. Five fixtures (new tracked, new untracked, deleted, mode-only, renamed), each must go red on a correct change.
- **[blocker] 4.2 ("Then restore the files").** MEASURED. The design does not say what the files are restored FROM or whether the index is touched. At `odd done` time the work is normally uncommitted. (a) Implemented with `git checkout <base> -- <paths>`: the probe shows it rewrites the index (a staged deletion was silently un-staged) and leaves added files in place. (b) Restoring from HEAD or via `git stash` discards or reshuffles uncommitted work, including unrelated work-in-progress that happens to sit under `in`. Result: lost edits, or a later plain `git commit` that commits base content while the working tree looks correct. *Fix:* State three rules in 4.2: (1) the journal is a byte copy of every path in the revert set (lstat-aware: type and mode), written and fsynced BEFORE the first file is changed; (2) the revert writes the working tree only, never the index (`git restore --source=<base> --worktree -- <paths>` was measured to leave the index unchanged; a temporary `GIT_INDEX_FILE` does the same on git older than 2.23); (3) restore copies back from the journal, never from git, then asserts each file's hash equals its pre-run hash, else exit 2. No stash.
- **[blocker] 2 (`base`), 4.2, 5 ("In CI ... This is the authority", "in-play").** MEASURED. (a) A depth-1 clone (the default of the usual CI checkout step) does not contain the recorded base: `git cat-file -e <base>` fails, so the gate that is 'the authority' returns 'could not run' on every pull request. (b) After `git rebase main` the recorded base still exists locally but is not an ancestor (`merge-base --is-ancestor` rc=1) and `git diff <base> HEAD` lists upstream files (probe: upstream `f` appeared). Result: 4.3 fails on files the outcome never touched (correct work REJECTED), and 4.2 reverts upstream edits inside `in`, producing a mixed tree that fails to import or compile, so ANY proof goes red (weak proof ACCEPTED). (c) After a squash merge the outcome files stay in `.odd/outcomes/` with bases that no longer exist; 'in-play' is not defined, so a later gate either re-verifies them (exit 2 forever) or not. *Fix:* Treat `base` as a hint: use it if `git merge-base --is-ancestor <base> HEAD`, otherwise fall back to `git merge-base HEAD <--base REF or default branch>` and print that it did. Define in-play as outcome files added or modified between that effective base and HEAD. `odd init --ci` writes `fetch-depth: 0` and passes `--base`. Base still unresolvable -> exit 2 with the exact fetch command. Fixtures: rebased branch, shallow clone, squash-merged history.
- **[blocker] 4.2 (journal), 11 (second bullet).** A proof that takes minutes runs inside an agent's shell tool, which kills long commands (the timeout is harness-specific; not measured here), or the terminal is closed, or the process gets SIGKILL. The tree is left at base content. 'Any later `odd` command restores' is not enough: (a) the agent sees its edits gone, redoes them, and the later restore overwrites the redone work with the journal copy; (b) `git commit -a` in between commits the reverted tree, and a pre-commit hook that restores the working tree does not change what that commit records, because the content is already staged; (c) two sessions running `odd done` at once interleave reverts and journals, so one run's reverted bytes are 'restored' as the original. *Fix:* Four small rules, no new command: (1) restore in a `finally` and on SIGINT/SIGTERM/SIGHUP; (2) every entry point, hooks included, that finds a pending journal restores and then exits 2 instead of continuing (the commit or push is refused once and re-run); (3) restore never destroys bytes: if a file on disk differs from what `odd` wrote at revert time, the displaced bytes are saved under `.odd/tmp/displaced/` and both paths are printed; (4) one lock file created with O_EXCL (pid and start time) so a second `odd done` or `odd gate --recompute` exits 2. Fixtures: kill -9 mid-proof then `git commit -a`; two concurrent runs.
- **[major] 4.2 first sub-bullet ("replaces ... the mutation step", "a weakened test ... is rejected").** Any non-zero exit on the reverted tree counts as red, so these are ACCEPTED (false red): (a) the kept test file imports a symbol the change added, then asserts nothing: ImportError on the reverted tree; (b) the proof's own entry file is inside the revert set (`proof: ./scripts/check.sh`, `in: scripts/**`): exit 127 once it is removed, whatever it checks; (c) the proof is killed on the reverted tree (OOM, exit 137); (d) a file moved from outside `in` to inside it, with the small deletion passing the trivial lane: the new path is removed, the old one not recreated, import fails; (e) a pre-existing test weakened to something base still fails (`sum == bill` becomes `len == 3`). So the check proves 'the proof depends on the change being present', not what the two claims say; a mutation step would catch (a) and (e). *Fix:* Reword the bullet to the true claim and move (a) and (e) to section 11. Classify exit 126/127, death by signal and timeout as 'could not run' (2), not red. If rename detection pairs a path inside the revert set with one outside it, exit 2 with 'widen'. Store the red run's exit code and last 20 output lines in the evidence and print them, with the list of test files that existed at base and were modified or deleted. No mutation machinery.
- **[major] 4.2 second sub-bullet ("the environment ... is identical; a failure is due to the content").** MEASURED for Python. A one-character fix (same file size) reverted within the same second as the green run: Python reused the cached bytecode of the changed version (probe printed 1 after the source was rewritten to return 2), so the proof passes on the reverted tree and a correct outcome is REJECTED; the mirror case after restore leaves base bytecode behind a correct source, so the next green run or the next outcome in a CI recompute fails. A restore that preserves the original mtime (copy2, rename back) has the same effect on timestamp-based builders (make, `tsc -b`): outputs built from reverted source look up to date. Separately, a proof that writes tracked files during the red run (codegen, snapshot update, lockfile) leaves base-derived files after restore. *Fix:* One implementation rule: every revert and restore write sets mtime to max(now, the last mtime this run gave that path) plus 2 seconds; never preserve mtimes (probe: +2s made Python pick up the new source). One check: compare `git status --porcelain -z` before the revert and after restore; a difference is exit 2 naming the files. Replace the sentence with 'state outside tracked files (installed dependencies, build outputs, caches, databases, daemons) is neither reverted nor restored'. Content-hash caches (Gradle, Bazel, `tsc --incremental`) need nothing; that is expected, not measured here.
- **[major] 4.2 (revert set) and third sub-bullet (`counterfactual: skip`, `max_skips`).** Correct outcomes REJECTED (false green) because taking the files out changes nothing the proof can see (none measured here; each needs a fixture): (a) dependency-only change: `package.json` and lockfile reverted, `node_modules` still holds the new version; (b) checked-in generated file under an exempt path or outside `in` is not reverted; (c) change-selective runners (`jest -o`, affected-only, test-impact plugins) see no difference from HEAD on an uncommitted revert, run zero tests and exit 0; (d) tests in the same file as the product (Rust `#[cfg(test)]`, doctests) vanish with the revert and a filtered run of zero tests exits 0, while a runner that exits non-zero on zero tests gives the opposite error; (e) the change is only in `tests`: the revert set is empty, the proof is run a second time for nothing and the message blames the proof. - **[major] 4.2 and 4.3 ("some in-play outcome's `in`"), 8 (per-outcome stats).** Outcomes A and B both have `in: src/billing/**` and both edited `split.py`. - **[major] 4.2 implementation choice: who writes the reverted files (binary, filters, symlinks, modes).** If the tool reads blobs with `git show <base>:<path>` and writes them itself: text mode corrupts binary files; a Git LFS file is written as its pointer text and an `autocrlf` tree gets LF content, so a proof that reads the asset or checks formatting fails for the wrong reason (ACCEPTED); a symlink becomes a regular file holding the target path (MEASURED: `git show` of a symlink prints `a.py`), and a journal made with a link-following copy restores a regular file where the link was; a `chmod +x`-only change is not reverted if only content is compared, so `proof: ./run.sh` still passes (REJECTED). *Fix:* Let git write the reverted versions for modified and deleted paths (`git restore --source=<base> --worktree -- <exact paths>`; the probe shows it restores content, mode, symlink and a deleted file and leaves the index alone), and have the tool only move added and untracked paths aside. Journal copies use lstat and recreate links as links. Fixtures: binary file, symlink, mode-only change. LFS and autocrlf not measured here.
- **[major] 4.2 run on Windows; 7 ("The tool: `odd` in the shell ... same").** Not measured here (no Windows host); each needs a fixture on a Windows runner. (a) A `proof:` line run through the platform shell means cmd.exe: `./check.sh`, `test -f x`, single quotes and `VAR=1 cmd` written on macOS or Linux fail the green run for every Windows contributor (REJECTED). (b) A file held open by an editor, antivirus or a daemon the proof started cannot be replaced: the revert stops half way, and running the proof on a half-reverted tree gives a red that is ACCEPTED. (c) A case-only rename on a case-insensitive filesystem: writing the old name and then deleting the new one deletes the file just written. (d) Hashing working-tree bytes gives different evidence hashes for CRLF and LF checkouts, so committed evidence is always stale on the other OS. (e) MEASURED on Linux: without `-z`, git prints `"src/caf\303\251.py"` for a non-ASCII path, which matches no glob and no file. *Fix:* Run proofs through the `sh` that ships with Git on Windows (git is already required), so there is one shell everywhere. Any error while reverting -> restore and exit 2; the proof is never run on a partial revert. Do removals before writes. - **[major] 4.2 cost; 5 last line ("the same command in a `pre-push` hook").** Each verification is two proof runs. **Keep:** (1) The differentiator itself: done = the proof passes on the tree as it is and fails with the change taken out, recomputable from the repository alone.
